# Workflow Service

Workflow orchestration service powered by Windmill. Translates internal DAG format to Windmill OpenFlow, manages workflow lifecycle, and tracks executions.

## Commands
- `npm test` — run all tests (Vitest)
- `npm run test:unit` — unit tests only
- `npm run test:integration` — integration tests only
- `npm run build` — compile TypeScript + generate OpenAPI spec
- `npm run dev` — local dev server (tsx watch)
- `npm start` — start production server
- `npm run generate:openapi` — regenerate openapi.json from Zod schemas

## Architecture
- `src/routes/workflows.ts` — CRUD workflow endpoints
- `src/routes/workflow-runs.ts` — Execution + status endpoints
- `src/lib/windmill-client.ts` — HTTP client for Windmill REST API
- `src/lib/dag-to-openflow.ts` — Core: translates our DAG → Windmill OpenFlow
- `src/lib/dag-validator.ts` — Validates DAG structure before translation
- `src/lib/node-type-registry.ts` — Maps node types to Windmill script paths
- `src/lib/input-mapping.ts` — Translates $ref syntax to Windmill input transforms
- `src/lib/job-poller.ts` — Background polling of running Windmill jobs
- `src/lib/periodic-cleanup.ts` — 24h interval re-running stale-deprecation + Windmill orphan-flow cleanup
- `scripts/nodes/` — TypeScript scripts deployed to Windmill (one per node type)

## Key concepts
- Our DAG format: `{ nodes: [{id, type, config, inputMapping}], edges: [{from, to, condition?}] }`
- Windmill OpenFlow: `{ value: { modules: [...] }, schema: {...} }`
- Input mapping: `$ref:node-id.output.field` → `results.node_id.field` in Windmill
- Node scripts in Windmill call our existing services via HTTP
- Stubs throw errors with clear messages until the real service is built
- **Windmill job retention** (`completed_job` rows) is set instance-wide at boot via `POST /api/settings/global/retention_period_secs` with value 604800 (7 days). The API requires the Windmill token to be superadmin; we log a warn but do not block boot if it isn't. CE caps retention at 30 days — anything over is clamped server-side.

## Rules
- **An api-key-only / org-less route MUST be mounted BEFORE the global `app.use(requireIdentity)` gate (`src/index.ts:36`) — an inline `requireApiKey` on it is NOT enough.** `requireIdentity` is applied globally right before `workflowsRoutes`/`workflowRunsRoutes`, so ANY route inside those routers runs `requireIdentity` FIRST and 400s (`"x-org-id, x-user-id, and x-run-id headers are required"`) when identity headers are absent — the route's own `requireApiKey` never gets a chance. Public / cross-org / service-to-service reads (identified by service api-key, no per-user identity) belong in `src/routes/public-workflows.ts` (mounted at `src/index.ts:30`, before the gate) or `src/routes/internal.ts` (line 33). A dynasty slug is a global cross-org identifier, so `/workflows/dynasty/slugs` lives in the public router even though its path is under `/workflows`. (Fixed v0.38.0, #341 — was shadowed inside `workflowsRoutes`, breaking runs-service/email-gateway public dynasty-cost filters; features-service#526.)
- **The three dimension tags (`category`, `channel`, `audienceType`) are PROVENANCE — extend the vocabulary, never borrow a value that is false.** Nothing downstream branches on them: api-service and distribute.you type them as plain strings, the MCP passes them through, and a fleet-wide grep finds no consumer that compares one to a literal. That is exactly why a wrong value survives — it breaks nothing and outlives whoever wrote it. So when a new channel family arrives and no existing value is true of it, WIDEN the enums in `src/schemas.ts` (additive: no consumer parses them as a closed set) and teach `src/lib/prompt-templates.ts` the new values in all three places it lists them. Paid reach was the first such family: `category: "advertising"`, `channel: "ads"`, `audienceType: "audience-targeting"` — it sends no email, builds no database, and describes its audience to an ad platform as targeting criteria rather than contacting anyone. The 966 pre-existing rows (`sales|pr|outlets` × `email|database` × `cold-outreach|discovery`) keep their meaning untouched. `generateWorkflow` now parses the model's three tags against the same enums and retries, then throws `GenerationValidationError`, rather than storing whatever it invented.
- **The `ai-meeting-booking` channel is the fleet's first CONVERSATION-FOLLOW-UP workflow, and almost everything it does belongs to somebody else.** `src/lib/ai-meeting-booking-dag.ts` + `scripts/seed-ai-meeting-booking.mjs` answer ONE prospect per run: claim, read, draft, send, record. Three of those five are other services' jobs and must stay that way. WHO to answer, in what order, and when to stop is lead-service's follow-up queue (`POST /orgs/campaigns/{campaignId}/followups/claim-next` — atomic conditional UPDATE, oldest-due-first, opt-out / booked-meeting / answered-again all honoured there); do not re-derive any of it here, and note that a run which claims nobody cannot structurally reach the send, which is what makes two concurrent runs safe. WHICH MAILBOX answers is instantly-service's (`POST /orgs/replies` resolves it from the mailbox that originally contacted them — supplying a from-address is the exact failure that endpoint exists to prevent, so the DAG passes only `campaign_id`, `email`, `body_html`). And the NEXT DUE DATE is stored, never derived: the interval grows 3/7/21/60/180 days with no cap on the number of follow-ups, but a prospect who writes "recontact me in January" must be honoured, so the model chooses the date and lead-service keeps it.
  Two orderings in that DAG are load-bearing. The record comes strictly AFTER the send — a follow-up recorded first would move the count for a reply that never went out. And `resolve-next-due` bounds the model's date against the range lead-service publishes (strictly future, at most a year) BEFORE the write: that 400 would otherwise land after the irreversible step, leaving the prospect answered with no record, their claim expiring, and the queue handing them out to be answered a second time. It is the one place in this file where an unusable value is replaced rather than thrown on, and it logs loudly when it does.
  The booking link is per FUNNEL, not per brand (a brand selling several funnels has a different one for each): `GET /campaigns/{id}` states the campaign's `offerId` + `funnelKey`, and brand-service's `GET /internal/offers/{offerId}/sales-funnels` carries `bookingUrl` on the matching funnel. Slots are read straight off Calendly's PUBLIC booking API — two unauthenticated GETs, no key and no OAuth, and passing the prospect's IANA timezone returns the slots ALREADY CONVERTED, so there is no timezone arithmetic here. Both public URL shapes resolve (`calendly.com/<user>/<event>` and the short `calendly.com/d/xxx`). That API is UNDOCUMENTED and will break one day without notice, which is why every failure in `readBookingSlotsCode` is a DEGRADATION and never an exception: the prospect still gets an answer carrying the plain booking link (or, when the brand has no link for that funnel, a question about their own availability), logged loudly. That is the ONLY fallback in this workflow; everything else lands on the error branch. Calendly's official API cannot serve this — it needs the customer's own OAuth and a paid plan — and Cal.com / HubSpot / SavvyCal are deliberately not read yet: an unknown host degrades rather than guessing.
  The LLM call goes through chat-service `POST /complete` (which owns the model resolution, the provider key AND the cost declaration), never a provider SDK. Because `/complete` takes one flat `message`, the prompt is assembled by a `script` node rather than by input mappings — which is also what makes it readable in the stored DAG.

- **The columns are NULLABLE and the request schema calls them optional — keep those two in agreement.** Migration 0007 made them NOT NULL while the request schema (and Drizzle's own `src/db/schema.ts`) said optional, so omitting one passed validation and died in Postgres as a generic 500 the caller could not act on. Migration 0035 drops the NOT NULL. `src/lib/db-error.ts` maps a Postgres 23502/23514 to a 400 that NAMES the column (as its camelCase request field) on every write path; anything it does not recognise still takes the existing 500. If you ever make one of these required again, make the request schema say so — a field the API calls optional must be omittable.

- Never edit `openapi.json` manually — regenerate with `npm run generate:openapi`
- Commit `openapi.json` alongside schema changes in `src/schemas.ts`
- **`zod-to-openapi` does not support `z.lazy()`.** `npm run generate:openapi` throws `UnknownZodTypeError: ZodLazy` and aborts. Forward references between schemas inside `src/schemas.ts` must be resolved by **declaration order** — define the referenced schema (e.g. `ProviderInfoSchema`) ABOVE the schema that uses it (e.g. `WorkflowListItemSchema = WorkflowResponseSchema.extend({ requiredProviders: z.array(ProviderInfoSchema) })`). When you hit the error, move the dependent block lower in the file, not the dependency higher — the dependent is usually a small `.extend(...)`, while the dependency is referenced from many places.
- When adding a node type: update `node-type-registry.ts` + create script in `scripts/nodes/`
- Every bug fix must include a regression test
- **All three creation paths now refuse a duplicate signature cleanly — keep it that way, and keep ops scripts idempotent anyway.** `PUT /workflows/{id}` (fork) and `POST /workflows` both check `(feature_slug, signature, status='active')` BEFORE touching Windmill and answer 409 with the existing workflow's id; `POST /workflows/create` (LLM path) is idempotent on `(orgId, featureSlug, signature)` and answers 200. The guard exists because the partial unique index `idx_workflows_active_sig` would otherwise be violated by the insert and leak a raw Postgres 500 (which is what `POST /workflows` did until #378). The check is deliberately NOT org-scoped — the index isn't either — and must stay ahead of `createFlow` so a conflict leaves no orphan flow. A seeding/ops script should still read the feature's active workflows first and skip the cells it already covers: a 409 per already-covered cell is noise, and pre-reading is what lets a rate-limited batch resume. Reference impl: `scripts/seed-feedback-request-matrix.mjs` (reads `GET /workflows?featureSlug=&status=active`, derives each row's `(prompt type, model)` cell from its stored DAG, creates only what is missing). The same idempotence is what makes the route's **10-creations-per-minute-per-org** rate limit (`createRateLimit`, `src/middleware/rate-limit.ts`) a non-event: a batch of more than 10 ends on 429s, and re-running after the window creates only the remainder. Do not retry the 429 in-process; let the run fail loudly and re-run, or a rate-limited batch reads as a clean one. Note when deriving a cell that an ABSENT `config.body.model` means the chat-service default (`pro`), not "no model" — reading it as absent makes an already-covered cell look missing and duplicates it.
- **A `$ref:flow_input.X` whose `X` nobody puts in `flowInputs` fails SILENTLY — it renders as an empty string, raises nothing, and logs nothing.** This is a different bug from "the DAG never maps the variable", and it is invisible to the audit that catches that one: the mapping is present and looks correct. `currentDate` was in exactly this state — 49 active workflows mapped `$ref:flow_input.currentDate`, the dispatcher never supplied it, and **1402 of 1402** content-generation jobs carried `currentDate: ""`, so every prompt read `Today is .` for months. Fixed at the source (`flowInputs` in `src/routes/workflow-runs.ts`), which repairs every stored DAG at once without rewriting any of them. **When adding a flow_input reference, the check is not "is the variable mapped" but "is the key present in `flowInputs`"** — and the two audits must both be run: compare each active DAG's `body.variables.*` keys against the template's declared `{{variables}}` (catches unmapped), AND compare every `$ref:flow_input.*` against the keys `flowInputs` actually builds (catches unsupplied). Query the rendered truth in `content_generation_service.email_generations.prompt_raw` / `content_generations.prompt_raw`, which stores the exact string sent to the model — that is what turns "probably fine" into evidence.
- **A lead `$ref` names a NESTED shape: `lead.data.currentTitle` and `lead.data.organization.<field>` — never a flattened `lead.data.organization<Field>` or a bare `lead.data.title`.** lead-service `POST /orgs/buffer/next` serves the canonical lead under `lead.data` (FullLead) with the employer as a nested `organization` object; the head count is `organization.estimatedNumEmployees`, not `.size`. Seven LLM-authored workflows (`blind-discovery-email-v5..v14`) instead carried the flat spelling for eight fields, and a `$ref` to a path the producer does not serve renders as an empty string with no error and no log line — so leadCompanyName / Size / Industry were empty in 21% of all sales generations and leadTitle in 45%, for months. **The guard already exists and must stay:** `validateWorkflowEndpoints`' deep output-path check walks each `$ref` against the producer's live response schema and reports a miss as an ERROR, and `validateClientDag` runs it on every write path, so this class is unstorable today — the seven rows predate it. The repair is `src/lib/lead-context-mapping.ts` + `scripts/repair-lead-context-refs.mjs`: it derives each rewrite from the workflow's OWN mappings and accepts a candidate only when the repaired path RESOLVES against the live spec, reporting rather than guessing when none does. Do not hardcode a rewrite table keyed on workflow id, and do not relax the deep-path check to a warning.
- **content-generation publishes TWO variable lists, and only one of them is a contract — map the second one in full.** `GET /platform-prompts?type=` answers with `variables` (the tokens the stored body declares; a missing one is an error) AND `contextVariables` (optional lead + organization facts every template accepts and renders into a "Recipient context" block ahead of the body). A caller that sends none of the second list gets the prompt it always got, byte for byte — which is exactly why the gap survived: nothing errors, nothing logs, and 31 active email workflows wrote cold email off five lead facts while lead-service served thirty-three of them. So a workflow that maps a context variable is COMPLETE, not over-providing: `validateTemplateContracts` accepts a provided name found in either list and requires only the first, and any code here comparing provided-vs-declared variables must read both or it reports a correct workflow as wrong. The catalog is read LIVE (`contextVariables` on the prompt read) and never restated; what this repo states is the PATH each name resolves to, in `src/lib/lead-context-variables.ts`, and every path is checked against lead-service's live response schema before it is written — a name the served shape cannot satisfy is reported, never guessed at. The lead ROOT is derived per DAG from that workflow's OWN existing refs (the active DAGs are not uniform), same discipline as the part-1 repair. `scripts/backfill-lead-context-variables.mjs` writes them onto the stored heads (dry-run default, idempotent, per-row `x-org-id`, paced under `createRateLimit`) and `src/lib/prompt-templates.ts` teaches the generator the same set so new workflows are born complete. Note two arrays are mapped straight through rather than reshaped: `employmentHistory` and `fundingEvents` carry lead-service's own keys (`organizationName`/`startDate`), not the illustrative `company`/`start` in content-generation's descriptions — its renderer humanises whatever keys an object carries, so a `script` node would buy nothing and would change the topology of 31 live workflows.
- **A brand extract-field ref MUST end in `.value`.** `POST /orgs/brands/extract-fields` answers `{fields: {<key>: MultiBrandFieldValue}}`, so `$ref:...output.fields.<key>` hands the LLM the whole envelope: the value, plus `byBrand`, `cached`, `expiresAt`, `sourceUrls`. Nothing is lost and nothing errors, which is why it survives unnoticed — 592 of 1398 PR generations rendered raw JSON with cache metadata into the prompt. `pr-cold-email-outreach-iris` is wired this way and is nonetheless the fleet's best cost-per-positive-reply, so the wiring is a quality issue, not a breakage. Always emit `.value`.
- **Always forward ALL downstream headers.** Every service-to-service call MUST spread `DownstreamHeaders` (from `src/lib/downstream-headers.ts`) into the fetch headers. Never cherry-pick individual headers — use `extractDownstreamHeaders(req)` in routes and pass the full object through. Missing headers don't always crash, but they silently break tracing and logging in downstream services.
- **Brand business fields come from `POST /orgs/brands/extract-fields`, NOT from `GET /internal/brands/{id}`.** The GET endpoint returns only the canonical minimal shape (`id`, `domain`, `url`, `name`, `logoUrl`, `createdAt`, `updatedAt`) — anything else (industry, companyOverview, valueProposition, targetAudience, mission, bio, etc.) must be requested via the extract-fields POST with an explicit `body.fields: [{key, description}]` array. The LLM workflow generator's example DAG in `src/lib/prompt-templates.ts` is the canonical pattern (the `brand-extract` node + three precise field descriptions for cold-email content). When a workflow needs a new brand-derived variable, extend the `fields` array — do NOT add a custom node script and do NOT fall back to the GET endpoint. Use `/orgs/brands/extract-fields` (org-billed) for workflow-service callers because Windmill auto-injects `x-org-id`; reserve `/internal/brands/extract-fields` for workers/crons without an org identity.
- **Windmill `rawscript` (bun/deno) requires `export async function main(...)`.** The `script` node type sends `config.code` verbatim into a Windmill `rawscript` module. Windmill executes the code by calling `main(...)` with positional arguments derived from `input_transforms`. A bare top-level `return {...}` compiles in JS but rawscript rejects it at runtime — the workflow 500s on first invocation. Every example added to `src/lib/prompt-templates.ts`, every fixture in `tests/helpers/fixtures.ts`, and every test asserting `rawscript` content MUST use the `export async function main(...) { ... }` shape. Each key in `inputMapping` becomes a positional argument of `main` in declaration order.
- **A field the send path needs travels ONLY if the authoring prompt names it — and fixing the prompt does not fix the DAGs already stored.** Workflows are LLM-generated from `src/lib/prompt-templates.ts` and then frozen; a field the prompt never mentions is absent from every workflow ever generated, and nothing errors — the downstream service silently applies its own default. So a "forward X to service Y" change is always TWO halves: the prompt (stops the bleeding for new workflows) plus a repair of the stored DAGs of every ACTIVE workflow (deprecated ones are never executed). The repair MUST derive its `$ref` from each workflow's OWN existing mappings — the active DAGs are not uniform (some resolve the recipient off a `lead`, some off a `journalist`, and the nesting differs even inside one group) — and the path from that root must be read off the PRODUCER's served shape, not inferred from a sibling field's depth (lead-service nests the canonical lead under `lead.data`, so `lead.data.timezone` is right even in a DAG that reads `lead.firstName`). A producer that serves no such field is skipped, not guessed at — a `$ref` the fetch node never returns is worse than the gap. Reference impl: `src/lib/recipient-timezone-mapping.ts` + `scripts/backfill-recipient-timezone.ts` (dry-run, idempotent, validates each rewrite with `validateDAG` + `validateWorkflowEndpoints` against live specs before writing, re-reads the row after). Boot's `syncFlowToWindmill` re-pushes every active DAG, so the repaired mapping reaches Windmill on the next deploy — no workflow re-create. (Shipped: recipient `body.timezone` → email-gateway → instantly-service, 23 of 27 active; the 4 `pr-*` workflows fetch from journalists-service, which serves no timezone.)
- **Re-pointing a fleet at a new prompt template is an UPGRADE per dynasty, and three lifecycle shapes need three different call sequences.** `POST /workflows/upgrade` resolves its target by `workflow_dynasty_slug` AND `status='active'`, so it 404s on a lineage whose versions are all deprecated. A sweep therefore cannot treat the fleet as one list: a LIVE dynasty is upgraded directly; a PARKED one (dynasty active, no active version, e.g. a model-variant fork created and never switched on) needs `PUT /workflows/{id}/status` to active, then the upgrade, then the new head parked again; a RETIRED one needs `PUT /workflows/dynasty/{slug}/status` to active, then the upgrade, then retired again (the upgrade insert carries `workflowDynastyStatus` over from its predecessor, so the re-retire is what flips the per-version axis back). Two details that bite: the new row takes its `orgId` from the CALLER's `x-org-id`, not from the predecessor, so a sweep must send each row's own org or the successor lands under the wrong one; and the whole path is behind `createRateLimit` (10/min/org), so a sweep of more than ten paces itself instead of retrying a 429. Reference impl: `scripts/retemplate-cold-email-signoff.mjs` (dry-run by default, skips a dynasty whose head already runs the successor template, so an interrupted run is simply re-run). Used to move 21 dynasties off the `cold-email-v27/28/29` family, whose prompts prescribed a `"Kevin from [ClientName]"` sign-off that contradicted the agency footer email-gateway appends downstream.

- **Propagating context to Windmill node calls has THREE shapes: dispatch-time `flow_input`, mid-DAG result-threaded (inline), and mid-DAG result-threaded INTO a for-each loop body.** Identity/tracking context known at execute time (orgId, userId, runId, campaignId, brandId, featureSlug, goal, …) is passed as `flow_input.*` and auto-injected into every node's `input_transforms` by `nodeToModule`/`buildFailureModule` in `src/lib/dag-to-openflow.ts`. But context chosen MID-flow by a node (e.g. the per-run `audienceId` that campaign-service selects inside `/start-run`, AFTER the root run is created) is NOT a flow_input — it must be threaded forward from the producing node's RESULT: detect the node, then auto-inject `results.<producer_module_id>?.audienceId` into every node DOWNSTREAM of the producer. **Scope the injection to the producer's edge-descendants ONLY — do NOT inject into the producer itself or any node that runs at-or-before it.** Windmill resolves a `results.X` reference by FETCHING the flow result by id BEFORE the JS `?.` guard evaluates, so the optional-chaining does NOT protect an upstream node: a node that runs before the producer (e.g. the chassis `gate-check` preceding `start-run`) 404s the result lookup at dispatch (`Not found: Flow result by id not found ... id: start_run`) — harmless to the run (yields `undefined`, flow completes) but spams a WARN on every campaign run. `getAudiencePropagationScope`/`descendantModuleIds` in `src/lib/dag-to-openflow.ts` compute the forward-reachable set from the producer's edges and gate the injection on it (fixed PR #318). Do NOT try to stamp such values on the root `execute-workflow` run or add them to `buildCampaignAttributionContext` — that context is built at dispatch where the value is still null and would mis-stamp the untagged root run. Propagating ANY new value to downstream node HTTP calls touches THREE surfaces in lockstep: (1) the auto-inject in `dag-to-openflow.ts`, (2) the `audienceId?`-style param + header line in EVERY `scripts/nodes/*.ts` that builds identity headers (Windmill maps `input_transforms` keys → params by NAME, so position is free), and (3) the `DOWNSTREAM_HEADER_KEYS` allowlist in `src/lib/downstream-headers.ts`. Inside it, `flow_input.*` (top-level) and `flow_input.iter.value` (current element) resolve, but `results.<outerStep>` does NOT — so the inline `results.start_run?.audienceId` transform yields `undefined` on per-lead gen/send nodes nested in a for-each-lead loop, leaving their runs cost UNTAGGED (the real #321 root cause; `branchone` is inline and DID resolve, which is why the earlier note thought it worked). []).map(el => el && typeof el === "object" ? {...el, __wf_audience_id: results.start_run?.audienceId} : el)`), and every loop-body node reads it back as `flow_input.iter.value?.__wf_audience_id` (const `AUDIENCE_ITER_KEY`/`LOOP_BODY_AUDIENCE_REF`). The `audienceRef` expression is threaded through `buildModules → buildConditionModule`(unchanged, inline)`/buildForEachModule`(overrides to the iter ref)`→ nodeToModule`. Workflow identity (`x-workflow-slug`) needs NO special handling for loops — it rides `flow_input.workflowSlug`, which IS in scope inside a subflow. When threading ANY new mid-flow value that must reach loop-body nodes, use the iter-fold, not `results.<producer>`. NOTE the two Windmill scoping facts diverged from a research subagent's doc-inference (which claimed outer `results` are flow-global and accessible in loops) — prod evidence (#321: loop-body cost untagged) is authoritative over the docs here.**
- **Validation judges literal request-body VALUES, not just field names — a value the target schema forbids is an ERROR, never a warning.** `validateWorkflowEndpoints` resolves each downstream OpenAPI request schema anyway, so when a leaf declares a closed set (`enum` / `const`, including array `items`), a value the DAG states LITERALLY is checked against it (`extractLiteralBodyValues` + `checkLiteralAgainstSchema` in `src/lib/validate-workflow-endpoints.ts`, `getSchemaAtPath` in `openapi-schema-resolver.ts`). This exists because "valid: true" is the only gate between an LLM-authored DAG and production: an LLM invented a model id in a `content-generation POST /generate` body, validation passed on shape alone, and three workflows were created carrying a value the service 400s on. Two boundaries hold the check honest and must stay: (1) only literals are judged — a value arriving from an upstream node (`inputMapping` `$ref`, including one that overrides a static base, and a whole-body `inputMapping.body`) is unknowable at validation time and gets no error AND no warning; (2) silence in the schema means unconstrained — never reject a value the schema says nothing about. Severity is `error` deliberately: `valid` flips only on errors, so a warning here would reproduce the incident verbatim.
- **Every path that STORES a client-supplied DAG runs the full gate — `validateClientDag`, never a bare `validateDAG`.** `validateDAG` reads topology only and says nothing about whether the endpoints the nodes call are real; `validateWorkflowEndpoints` is what resolves the live OpenAPI schema and judges paths, methods, required fields and literal values. For a while only the LLM generation path ran the second one, so `POST /workflows`, `POST /workflows/upgrade` with a client `dag`, and BOTH branches of `PUT /workflows/:id` (same-signature update AND fork) stored whatever passed topology — which is exactly how three workflows came to carry `"model": "deepseek-flash-v4"` (#372). `src/lib/validate-client-dag.ts` is the single gate all four call; a new write path that accepts a DAG calls it too. **Its permissiveness on a MISSING spec is deliberate and must not be tightened into an error:** `fetchSpecsForServices` settles every fetch and returns only what succeeded, so a service absent from the map is indistinguishable from a service whose fetch failed — treating absence as "unknown service" would 400 every workflow write during a registry blip. Absence therefore skips the endpoint check and logs the skipped services; a genuinely nonexistent service is still reported by `POST /workflows/:id/validate`, the boot validator and the spec watcher. Tightening this needs the fetcher to distinguish a 404 from a transport failure first.
- **Integration-test DB mock `.where()` ignores predicates — feed every SELECT via `mockSelectResponses`.** `tests/integration/*.test.ts` mock `src/db/index.js` with a dumb `.where()` that returns the whole `mockDbRows` array (or shifts the next `mockSelectResponses` queue entry) regardless of the WHERE clause. When you ADD a new `db.select()` to a route handler, every existing test that exercises that route's path now performs one extra SELECT — if it relied on the `mockDbRows` fallback it will get the wrong rows back (e.g. a signature-conflict check echoing the row being upgraded → false 409). Fix: in those tests push one `mockSelectResponses` entry per SELECT in order (`mockSelectResponses.push([dynastyRow], [])` = lookup hit, conflict miss). Don't add id/predicate guards to production code just to satisfy the dumb mock. Two further traps in the same mock: it also ignores the WHERE on `update()`, applying every `.set()` to the LAST row of `mockDbRows` only — so a route that updates several rows at once cannot be asserted row-by-row there, and its multi-row behaviour belongs in a unit test or a prod verification instead. And a route that opens a `db.transaction(...)` 500s against the mock unless it provides one; the mock object therefore has to be built with `vi.hoisted` and referenced from the `vi.mock` factory, because `vi.mock` is hoisted above module-scope `const`s and a plain `const mockDb = {...}` is still in its temporal dead zone when the factory runs.

## Database migrations

Migrations are **auto-applied on startup** via `drizzle-orm/postgres-js/migrator` (see `src/index.ts`), inside `boot()` — which runs **after** `app.listen()`. See "Boot order" below before touching `src/index.ts`.

**All migrations MUST go in `drizzle/`** — never create a separate `migrations/` folder. The startup migrator only reads from `drizzle/`.

When adding a migration:
1. Create `drizzle/NNNN_description.sql` (next sequential number)
2. Add an entry to `drizzle/meta/_journal.json` with the matching `tag` and next `idx`
3. Use `IF NOT EXISTS` / `DO $$ BEGIN ... END $$` guards to make migrations idempotent
4. Use `--> statement-breakpoint` between statements (drizzle convention)
5. Commit the migration file + journal update in the same PR as the schema change

## Boot order — the port binds BEFORE any database work

**Nothing may be `await`ed before `app.listen()`.** The database is a Postgres container on the shared box, and the first connection of a fresh process is the slowest one it will ever make — slower still when the box or the container has just restarted, or when the whole fleet redeploys at once and every service dials in together. Anything awaited before the bind spends the deploy's startup budget on that connection: the port never opens inside the deploy's healthcheck window, so the healthcheck fails and the deploy is rolled back, or the connection rejects outright and the process exits into a restart loop. The failure has nothing to do with the code being deployed, which is what makes it expensive to diagnose — it reads as a flaky deploy, you redeploy, the second attempt connects quickly, it passes, and the cause is never found. `tests/unit/boot-order.test.ts` asserts this at the source level (`awaits nothing before app.listen()`); it is the regression guard, do not relax it.

The startup block does only pure env inspection (`assertEnvironmentConsistency`), flips readiness to pending, registers shutdown handlers, binds, then calls `boot()`. Everything else — migrations, the API Registry health check, Windmill retention + node deploy, the job poller, `validateAndUpgradeWorkflows`, the SpecWatcher — lives inside `boot()`.

Three pieces hold it together:

- **`src/lib/migrate-with-retry.ts`** retries **only** connect-phase failures (`CONNECT_TIMEOUT`, `CONNECTION_CLOSED`, `ECONNREFUSED`, `ECONNRESET`, happy-eyeballs `AggregateError`s, `the database system is starting up`, …) with 250ms doubling backoff up to a 120s deadline. Nothing has run when a connection is refused, so the retry is write-safe. A **genuine** migration failure (bad SQL, constraint violation) is never retried and never swallowed — it marks the schema failed, logs `FATAL`, and exits.
- **`src/lib/schema-readiness.ts`** gates every DB-touching route behind 503 + `Retry-After` until migrations have been applied, so the early bind can never serve traffic against a schema the code does not expect. The flag defaults to `"pending"` — a process that never declares itself ready serves 503 rather than querying. **A new router that touches the database must be mounted BELOW `app.use(requireSchemaReady)`.**
- **`/health`** answers `200 {"status":"starting","migrations":"pending"}` while migrations are pending and **deliberately does not touch the database** — probing a database that has not finished connecting yet, from inside the healthcheck window, is the exact call that was blowing the deploy. Once ready it goes back to the live `SELECT 1` / Windmill checks, each bounded at 2s. Do not add an unbounded dependency probe to this route.

`src/db/index.ts` sets `net.setDefaultAutoSelectFamilyAttemptTimeout(5000)` — Node 20 gives each happy-eyeballs candidate address only 250ms, which is not enough for a database that does not answer instantly. Keep it. The 250ms budget was originally found to be too tight for a Neon compute resuming from suspend; Neon is gone, but nothing about the setting was Neon-specific — it is a Node-level default that is too aggressive for any slow first connect, including a Postgres container that has just come up. Do **not** add postgres.js `connect_timeout` (already defaults to 30s — a no-op) or `idle_timeout` (defaults to never closing an idle connection; setting it forces a fresh TCP+TLS handshake on the next request — a regression; that advice is correct for node-postgres, not postgres.js). Both were tried and reverted in brand-service#389.

Measured on 2026-07-31 against a database that never answers: pre-fix the port never opened and the process exited 1 at 30.3s; post-fix the port opened at 0.88s, `/health` answered 200 at 0.97s, gated routes returned 503, and the container stayed up retrying. Against the real staging database of the day (a then-Neon compute resuming from suspend) the pre-fix bind cost 2.14s — i.e. pre-fix, time-to-port-open simply *is* however long the first connection takes, whatever that happens to be that day. That is still the shape of the failure now; only the reason a first connection is slow has changed.

### No background loop may query the database unconditionally

**A loop that opens with a `SELECT` on every tick queries forever to learn there is nothing to do.** Every service in the fleet shares one Postgres container, so each such timer is permanent load on a shared resource, multiplied by however many services copy the pattern, in exchange for nothing on the ticks where no work exists. A poll that can only find work after something was written or dispatched should be started *by* that write or dispatch, not by a clock.

(This rule was originally written for Neon scale-to-zero, where a short-period `SELECT` loop pinned the compute awake and billed the whole period as active. Neon is gone and there is no compute to pin, so that reason is dead — the rule is not. The loops below are all still shaped this way, and the shape is still the right one.)

- **`JobPoller`** (10s) **stops itself** once no run is `queued` or `running`, and `wakeJobPoller()` restarts it from `markExecutionDispatched` — the single place a run becomes pollable. The `wokenDuringPoll` flag is load-bearing: it is cleared *before* the query so a dispatch landing between the query and the idle check cannot be swallowed. If you add another path that makes a run pollable, it must call `wakeJobPoller()` or that run is never reconciled.
- **`SpecWatcher`** runs hourly **and does not query on a tick that finds no spec drift**. The set of services the active workflows call is cached in memory; the steady-state tick is HTTP + a hash comparison, and Postgres is read only when the cache is cold or the specs genuinely moved (which is also when the DAGs are needed). Do not lower the interval, and do not reintroduce a `SELECT` at the top of the tick.
- **`PeriodicCleanup`** owns **no timer at all** — `noteWorkflowWrite()` calls `maybeRun()` from the write paths and it sweeps at most once per 24h. A retention sweep only has work when something was written, so on a quiet service it correctly never runs at all.

Both caches are dropped/driven by a single `router.use` hook at the top of `src/routes/workflows.ts` that fires on any non-GET request finishing 2xx, rather than at each individual write site — a write site added later is covered without anyone remembering. `markExecutionDispatched` calls `noteWorkflowWrite()` too, next to `wakeJobPoller()`, so run traffic keeps the sweep alive.

Before adding any `setInterval` that touches the database, ask what work it could possibly find on a tick where nothing was written and nothing was dispatched. If the answer is "none", the timer is the wrong trigger. On-demand or wake-on-write beats a timer.

**What this can and cannot buy — measured 2026-08-01, on the Neon deployment that preceded the current Postgres container.** The production compute (`ep-still-mud-a1319tcx`) was still `active` continuously after all of the above, and that was **not** a poller bug: prod dispatched **~2,900–3,500 workflow runs a day**, median gap between dispatches **22.8s**, and exactly **one** gap over 300s in 24h (max 356.8s). That left roughly *56 seconds* of idle quiet per day, so the ~182 CU-h billed was genuine execution, not poll-induced wakefulness — removing every timer in this repo would have saved ~0 while campaigns were running.

The billing frame is obsolete (there is no per-compute bill now), but the measurement's real lesson is not: **this service's own traffic almost never goes quiet, so the pollers are not where the load comes from.** Do not go hunting for database-load savings in the timers here — the lever is the *volume of real runs*. Verify before assuming otherwise: `SELECT` the inter-arrival gaps rather than reading the code.

**Failures inside `boot()` still exit the process** (API Registry unreachable, Windmill node deploy failure). This is the deliberate trade for binding early, and it has a diagnostic consequence: the port is already open and `/health` already answers 200 by the time `boot()` runs, so the deploy's healthcheck passes and no rollback is triggered — the process then dies *afterwards*, on its own. So when a deploy looks green but the service is unreachable, read the container logs for a post-listen `process.exit(1)` rather than assuming the deploy is fine. A green deploy says the port opened, not that boot finished.

## Workflow naming and versioning

Workflows follow a dynasty model: each workflow belongs to a lineage (dynasty) that tracks its evolution through upgrades. Names and slugs are derived from the `feature_slug` and a poetic `workflow_dynasty_signature_name` generated once per dynasty.

### Naming rule

The bare word `dynasty` does not exist in this repo — always `workflow_dynasty_*` (and `workflowDynasty*` in TypeScript). Never bare `signature_name` either: the column is `workflow_dynasty_signature_name` (Drizzle field `workflowDynastySignatureName`). Indexes prefixed `idx_workflows_*` stay as-is — the table prefix in the index name already disambiguates.

### Scope rule

`workflow_dynasty_signature_name` is unique among **all** workflows (any `status`, any `org_id`) within the same `feature_slug`. Once a name is chosen for a feature, it is burned for that feature forever — even after deprecation. The dedup query uses `WHERE feature_slug = ?` only — no `org_id` filter, no `status` filter.

### Database columns

| Column | Type | Unique? | Description |
|---|---|---|---|
| `workflow_slug` | text | Yes (globally) | Technical identifier, immutable once created. Used as API key for execution (`POST /workflows/by-slug/:workflowSlug/execute`). |
| `workflow_name` | text | Yes (globally) | Human-readable display name. |
| `workflow_dynasty_signature_name` | text | Unique per `feature_slug` (any status, any org) | Poetic word generated deterministically from the DAG hash. Set once at dynasty creation, never changes within the dynasty. Burned for life. |
| `workflow_dynasty_slug` | text | No | Stable lineage slug. Constant across all versions of a dynasty. |
| `workflow_dynasty_name` | text | No | Stable lineage display name. Constant across all versions of a dynasty. |
| `signature` | text | Unique per `(feature_slug, status='active')` | Hash of the DAG structure. Used for deduplication on upgrade. |
| `version` | integer | No | Version number within the dynasty. Starts at 1. |
| `feature_slug` | text | No | Reference to the feature in features-service. Passed by clients. |
| `status` | text | (partial unique index) | **Per-version** lifecycle. Within a dynasty the latest version is `active`, predecessors `deprecated`. Load-bearing for `idx_workflows_active_signame` + upgrade/execute resolution — do NOT overload for dynasty-level deprecation. |
| `workflow_dynasty_status` | text, NOT NULL, default `active`, CHECK in (`active`,`deprecated`) | No | **Dynasty-level** status, independent of `status`. Same value across all versions of a dynasty. Set via `PUT /workflows/dynasty/{workflowDynastySlug}/status`. Migration 0034. |

### Name composition

```
workflow_dynasty_slug = feature_slug + "-" + workflow_dynasty_signature_name
workflow_dynasty_name = TitleCase(feature_slug.replace("-", " ")) + " " + Capitalize(workflow_dynasty_signature_name)
workflow_slug         = workflow_dynasty_slug                        if version == 1
                      | workflow_dynasty_slug + "-v{version}"        if version >= 2
workflow_name         = workflow_dynasty_name                        if version == 1
                      | workflow_dynasty_name + " v{version}"        if version >= 2
```

Example with `feature_slug = "sales-cold-outreach"`, `workflow_dynasty_signature_name = "obsidian"`, version 3:
```
workflow_dynasty_slug: "sales-cold-outreach-obsidian"
workflow_dynasty_name: "Sales Cold Outreach Obsidian"
workflow_slug:         "sales-cold-outreach-obsidian-v3"
workflow_name:         "Sales Cold Outreach Obsidian v3"
```

No `-v1` or `v1` suffix for version 1 — the first version has no version suffix in slug or name.

### Lineage columns

Lineage is tracked by two forward-pointing columns on every workflow row:

| Column | Type | Description |
|---|---|---|
| `creation_type` | text, NOT NULL, CHECK in (`scratch`, `upgrade`, `fork`) | How this row was created. |
| `created_from_workflow` | uuid, nullable | Predecessor row id. Null only when `creation_type='scratch'`. |

The legacy `upgraded_to` and `forked_from` columns are gone. The successor of a deprecated row is found by reverse lookup: `SELECT id FROM workflows WHERE created_from_workflow = <deprecated.id> AND creation_type = 'upgrade'`.

### Retirement: dynasty status vs per-version status

There are TWO status axes and they must not be conflated:
- **Per-version `status`** (`active`/`deprecated`) — version lifecycle within a dynasty (latest active, predecessors deprecated). Load-bearing for the partial unique index + upgrade/execute forward-resolution.
- **`workflow_dynasty_status`** (`active`/`deprecated`) — the WHOLE lineage's retirement flag (staff action). Same value on every version row.

**"deprecated" MEANS "does not run", on either axis.** It used to mean that on neither: the dynasty flag was documented as purely informational, so `sales-cold-email-outreach-camellia-v2` — retired in June — went on generating email for a paying brand until 2026-08-24, and the person who retired it was told nothing. Whatever is added to this area later, keep the word and the behaviour in agreement. Retirement is written on BOTH axes at once and refused on both, because the two do different halves of the job:

- The **dynasty** axis is what the execute routes check (`refuseIfDynastyRetired` in `src/routes/workflow-runs.ts`, applied after resolution on both `POST /workflows/{id}/execute` and `POST /workflows/by-slug/{slug}/execute`) → 410, no substitution. It catches the row that is dynasty-retired while still marked version-active: an upgrade landing on a retired lineage, a restored backup, a hand-written UPDATE.
- The **per-version** axis is what every EXISTING CONSUMER already reads, and none of them can see the dynasty axis on the surface they use. campaign-service provisions a funnel campaign off `GET /workflows?featureSlug=&status=active` and never looks at the returned status field; features-service builds the projection campaign-service's greedy rotation consumes from `/public/workflows?status=all`, picking the head by `status === "active"`. So a retirement that only flips the dynasty column leaves the dynasty ranked, picked, and 410-ing on every run. **Do not "simplify" the dynasty route back to a single-column update.**

**Retire a whole lineage — `PUT /workflows/dynasty/{workflowDynastySlug}/status`** (api-service transparent-proxies it): body `{ status: "active"|"deprecated" }` → 200 `{ workflowDynastySlug, status, updatedWorkflows, activeWorkflowSlug }`. Idempotent. Unknown dynasty slug → 404. Retiring sets `workflow_dynasty_status` AND `status='deprecated'` on every version in one transaction, so `activeWorkflowSlug` comes back `null` — a retired dynasty has no executable version and nothing is substituted for it. Un-retiring restores exactly ONE version: the highest version number, which is the upgrade-chain terminal (forks branch into a new dynasty slug), so the partial unique index cannot be violated. Its Windmill flow is re-pushed BEFORE the row goes live, because `cleanupOrphanedWindmillFlows` deletes flows of deprecated workflows — restoring the row without the flow yields a live workflow that 404s inside Windmill on every execute. A flow that cannot be restored fails the whole call with 502.

**Retire ONE version — `PUT /workflows/{id}/status`**: body `{ status: "active"|"deprecated" }` → 200 with the full workflow. Until this existed, "retire this workflow" was reachable only by a direct database write — the upgrade path was the sole writer of the column. Retiring the only active version of a dynasty leaves it with no executable version, so execute-by-slug answers 410 rather than falling back to an older one. Re-activating is 409 when another version of the dynasty is already active, and re-pushes the Windmill flow first, same as above.

**Upgrading a retired dynasty does not un-retire it** — the upgrade insert carries `workflowDynastyStatus` over from the predecessor. Without that the column defaults to `active` and the new version silently starts running.

**Listing = the runnable set.** On both `GET /workflows` and `GET /public/workflows`, `status=active` (the default) means EXECUTABLE: version active AND dynasty active. `status=deprecated` is its exact complement (either axis deprecated) and `all` their union — `resolveStatusFilter` in `src/lib/status-filter.ts` is the single definition, used by both routes. A workflow that can no longer execute must not keep being offered as a candidate, or the picker chooses it and every run is refused.

**Read — `GET /workflows` list:** the emitted `status` field is OVERRIDDEN to the item's **dynasty** status per the locked contract (so the dashboard renders one active/deprecated flag per dynasty row). `workflowDynastyStatus` is exposed self-documenting on all workflow responses, and on `/public/workflows` items too — that route is how features-service sees the fleet, and the per-version status alone cannot tell an executable row from one whose lineage was retired. On single-workflow `GET /workflows/{id}`, `status` stays the per-version lifecycle value. When threading a new dynasty-level flag, add a column + write it on ALL lineage rows; do NOT overload `status`.

### Operations and behavior

**Creation — `POST /workflows/create`:**
- Body: `{ featureSlug, description, hints? }`. LLM generates the DAG.
- If an active workflow with the same `(orgId, featureSlug, signature)` already exists, returns 200 with that row unchanged (idempotent).
- Otherwise inserts a new row with `creation_type='scratch'`, `created_from_workflow=NULL`, `version=1`, no version suffix.
- This endpoint never upgrades existing dynasties.

**Upgrade — `POST /workflows/upgrade`:**
- Body: `{ workflowDynastySlug, description?, dag?, hints? }`. The input is the **stable dynasty slug** (constant across all versions of the dynasty), NOT a versioned `workflowSlug`. The route looks up the currently-active row via `WHERE workflow_dynasty_slug = ? AND status = 'active'`, so callers do not need to track which version is current after prior upgrades. **Exactly one of `dag` or `description` MUST be provided** (Zod refine enforces it; missing both → 400).
- Two DAG sources:
  - `dag` supplied → client-supplied DAG path. The LLM is **not invoked**. The DAG is run through `validateDAG` (rejects with 400 on invalid topology), its signature computed, and the rest of the flow is identical to the LLM path. `category`/`channel`/`audienceType` are **inherited from the existing row** (no LLM to infer them). `description`, if also provided, replaces the stored description on the resulting row. Use this for surgical edits (e.g. patch a single script node) without burning an LLM round-trip — the LLM-regen path tends to drift on small fixes.
  - `dag` absent → LLM path. `description` is required (min 10 chars) and `generateWorkflow()` regenerates the full DAG from it. `hints` is forwarded to the generator; ignored when `dag` is supplied.
- 404 if no active row matches `workflowDynastySlug`.
- If the new signature equals the existing one → in-place update, returns 200.
- Otherwise inserts a new row in the **same** dynasty (`workflow_dynasty_slug`, `workflow_dynasty_name`, `workflow_dynasty_signature_name` all unchanged — the dynasty signature name is immutable per dynasty) with `creation_type='upgrade'`, `created_from_workflow=existing.id`, `version=existing.version+1`, version suffix on `workflow_slug`/`workflow_name`. Returns 201.
- **Predecessor deprecation order matters.** The partial unique index `idx_workflows_active_signame (feature_slug, signature_name) WHERE status='active'` rejects two `status='active'` rows sharing `(feature_slug, signature_name)`. The upgrade route therefore wraps the deprecate+insert in a `db.transaction(...)` block and flips the predecessor to `status='deprecated'` **before** inserting the new active row. Windmill cleanup (deleting the predecessor's flow) runs **after** the DB commit so a rolled-back transaction does not leave Windmill in an inconsistent state.

**Fork — `PUT /workflows/{id}` with a DAG of new signature:**
- Inserts a new dynasty (new `workflow_dynasty_signature_name`, new `workflow_dynasty_slug`, new `workflow_dynasty_name`) with `creation_type='fork'`, `created_from_workflow=existing.id`, `version=1`.
- The source workflow is **always kept active** — there is no auto-deprecate-on-fork path.
- Returns 201.

**Metadata update — `PUT /workflows/{id}` with no DAG (or same signature):**
- Updates `description`, `tags`, etc. in-place. Returns 200.
- DAG-only changes that produce a new signature take the fork path above.

### Stats aggregation across lineages

Stats (costs, email metrics, completed runs) are aggregated by walking the upgrade chain in `getUpgradeChainIds()` (`src/lib/workflow-scoring.ts`):

- Linear walk from the active workflow back along `created_from_workflow`, only following `creation_type='upgrade'` edges.
- Stops at `creation_type='scratch'` (chain origin) and at `creation_type='fork'` boundaries (forks start a fresh dynasty for stats).
- A `visited` set prevents infinite loops on any pathological self-references.

The walker is fed the union of (active + deprecated) workflows so cross-dynasty convergence is followed naturally — when an upgrade was applied across dynasties, the chain crosses into the predecessor's dynasty and keeps walking.

### Feature naming

Workflow-service uses `feature_slug` directly to derive both the slug and the display name — there is no remote lookup, no `feature_dynasty_*` concept. The `featureSlugToName` helper titlecases the slug (`"sales-cold-outreach"` → `"Sales Cold Outreach"`) for display, and the slug itself is used verbatim in `workflow_dynasty_slug`. Clients only ever pass `featureSlug`.

### Execution resolves deprecated slugs forward to the active dynasty version

`POST /workflows/by-slug/:slug/execute` is "run the current live version of this dynasty," NOT "run this exact version." Callers (campaign-service) hold a **stable dynasty slug** = v1's `workflow_slug`, which becomes `deprecated` after the first upgrade. So the route MUST resolve forward: when the slug has no `active` row, it does a **direct dynasty-slug lookup** — `SELECT * FROM workflows WHERE workflow_dynasty_slug = <known.workflow_dynasty_slug> AND status='active'` — and executes that. This is O(1) and the active row is the upgrade-chain terminal (forks branch into a NEW `dynasty_slug`; the partial unique index `idx_workflows_active_signame` guarantees exactly one active per dynasty). Returns **410** only when the dynasty has zero active version; **404** only when the slug is entirely unknown. The response carries the actual `workflowSlug` executed, so the caller learns what ran. **Do NOT reintroduce a bounded reverse `created_from_workflow` walk** — the old `depth < 10` cap stranded any dynasty past v11 on a 410 (live prod stuck-loop: `sales-cold-email-outreach-tectonic` reached v16 → campaign re-claimed "stuck" forever, no emails). The bare-UUID route `POST /workflows/:id/execute` is the **pin-to-exact-version** path and deliberately does NOT auto-follow. (Fixed v0.35.1, #324.)
